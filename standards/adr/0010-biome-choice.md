# ADR 0010: Вибір Biome для форматування та лінтингу коду

* **Статус:** Прийнято
* **Дата:** 2026-09-28

## Контекст та проблематика

У класичному JavaScript/TypeScript стеку для забезпечення якості коду та єдиного стилю форматування зазвичай використовується зв'язка інструментів **ESLint** (лінтинг) та **Prettier** (форматування). 

Однак використання цього традиційного підходу має декілька мінусів:
1. **Складність конфігурації:** Необхідність налаштування та підтримки окремих конфігураційних файлів для кожного інструмента, а також встановлення специфічних плагінів для їх узгодження (наприклад, `eslint-config-prettier`, `eslint-plugin-prettier`).
2. **Перекриття залежностей:** Проєкт змушений підтримувати декілька великих npm-пакетів та їхніх залежностей.
3. **Швидкість роботи:** На великих кодових базах виконання лінтингу та форматування в CI/CD або під час commit-хуків може займати значний час.

## Рішення

Ми вирішили використовувати **Biome** як єдине рішення для форматування та лінтингу коду в проєкті, повністю відмовившись від **ESLint** та **Prettier**.

## Обґрунтування (Rationale)

Перехід на Biome обумовлений наступними перевагами:

1. **Мінімальний час налаштування та простіша конфігурація:**
   * Biome працює за принципом "zero-config out-of-the-box" із розумними дефолтними налаштуваннями.
   * Усі конфігурації зберігаються в одному єдиному файлі `biome.json`, який набагато простіший у підтримці ніж розгалужені конфігурації ESLint/Prettier.

2. **Заміна двох залежностей (2-in-1):**
   * Biome об'єднує функції форматтера та лінтера в одному інструменті.
   * Це зменшує кількість `node_modules` залежностей, спрощує оновлення та виключає можливі конфлікти між лінтером і форматтером.

3. **Висока швидкість виконання:**
   * Biome написано на Rust. За тестами розробників та спільноти, він працює в рази швидше за Prettier та ESLint, що суттєво скорочує час виконання перевірок local git hooks та CI/CD пайплайнів.

4. **Покращена інтеграція з VCS (Git):**
   * Biome має вбудоване розуміння стану VCS (наприклад, прапорець `--changed`), що дозволяє легко форматувати та перевіряти лише ті файли, які були змінені у поточній гілці або коміті, без необхідності складних сторонніх утиліт на кшталт `lint-staged`.

5. **Розширюваність та додаткові можливості:**
   * Biome містить корисні додаткові фічі "із коробки", такі як автоматичне сортування імпортів (Import Sorting), зручні швидкі виправлення (safe/unsafe fixes) та аналіз коду, що покриває майбутні потреби проєкту без встановлення додаткових плагінів.

## Наслідки (Consequences)

### Позитивні:
* Значно підвищилася швидкість перевірки коду на CI/CD та під час git hooks.
* Зменшилася кількість devDependencies у `package.json`.
* Спростився процес onboarding нових розробників завдяки єдиному файлу конфігурації `biome.json`.
* Відсутність конфліктів форматування між лінтером та форматтером.

### Негативні / Ризики:
* Екосистема Biome є молодшою порівняно з ESLint, тому деякі дуже специфічні кастомні правила ESLint можуть бути відсутні (але базового набору правил Biome повністю достатньо для більшості задач).
* Необхідність встановлення відповідного розширення (Biome VS Code / WebStorm plugin) для розробників.
