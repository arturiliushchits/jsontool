# ADR-0010: Вибір GitHub Actions, безплатного PaaS для staging та підходу до міграцій під SQLite

- **Статус**: Прийнято
- **Дата**: 2026-11-25

## Контекст (Context)
Потрібно налаштувати безплатний, простий і швидкий у підтримці CI з блокуванням мерджу та автодеплой на стейдж для застосунку **JSON Tool** (Node.js 22.13+, Express, вбудована БД `node:sqlite`, локальні Git-хуки + Biome), без підняття власного сервера, без SSH з GitHub Actions і без доступу CI до БД staging/prod.

## Розглянуті варіанти

### 1. Платформа CI та блокування мерджу
* **GitHub Actions + GitHub Branch Rules / Protection (обрано)**: безплатно для публічних репозиторіїв, нативна інтеграція з PR та статусами перевірок, не потребує окремої інфраструктури. Локальні Git-хуки залишаються для швидкого зворотного зв'язку розробника, а CI виступає обов'язковим бар'єром перед мерджем.
* **Зовнішні CI-сервіси (CircleCI, Travis тощо)**: зайва реєстрація та зайві інтеграції без переваг для поточного репозиторію.

### 2. Хостинг для CD (staging)
* **Безплатний PaaS Web Service (наприклад, Render) (обрано)**: не вимагає адміністрування власного сервера та SSH-ключів у GitHub Actions, підтримує Node.js 22.13+, автодеплой при пуші/мерджі в основну гілку та видає публічний URL.
  * *Компроміси безплатного тарифу*: можливий перехід інстансу у стан сну після простою, а локальний файл SQLite без окремого персистентного диска може скидатися при рестартах/перезбірках — для навчального/стейдж-контуру це прийнятно і явно задокументовано.
* **Власний VPS / Docker-хост зі скриптами по SSH**: більше ручної роботи з безпекою, оновленнями ОС та налаштуванням SSH-деплою, що суперечить вимозі «без SSH з GitHub Actions» і критерію простоти.
* **Serverless-платформи для статики/функцій (Vercel/Netlify)**: гірше підходять для класичного Express-сервера з локальним файлом SQLite.

### 3. Міграції та готовність сервісу
* **Розділення DDL, індексів і seed/оновлення даних + ідемпотентний запуск при старті + `/health` і `/version` (обрано)**: запобігає таймаутам при створенні індексів, виключає залежність CI від БД середовищ і дозволяє контролювати готовність інстансу до прийому трафіку.

## Наслідки
* CI запускає перевірки на ізольованих тестових БД всередині раннера та блокує невалідні PR.
* Пуш/мердж у цільову гілку автоматично оновлює стейдж, а `GET /version` дозволяє звірити SHA задеплоєного коміту.
* У `DEFENSE.md` фіксуються обмеження безплатного хостингу для SQLite та blue-green/readiness поведінки.
